## 1. 開発背景と課題（ペインの言語化）

### 1.1 開発背景：Linux デスクトップにおける「音声入力の空白地帯」
Windows（Whisper連携ツールやOS標準音声認識）や macOS（高品質な内蔵音声入力、MacWhisper等）では、日常業務やプログラミングを劇的に効率化する音声入力環境が急速に普及・進化している。
しかし、**エンジニア・開発者・リサーチャーが主戦場とする Linux デスクトップ（Ubuntu, Fedora, Arch 等）環境においては、実用に耐えうる日本語音声入力アプリケーションがほぼ存在しない「空白地帯」**であった。

### 1.2 ユーザーペイン（3大課題）
開発元および利用ユーザーが直面していた課題は以下の3点に集約される。

1. **OSデフォルト音声入力の致命的な精度の低さ**:
   - 専門用語、IT用語（例: `Kubernetes`, `PostgreSQL`, `Python`, `GitHub`）が不自然なカタカナ表記や誤字に変換される。
   - 文脈の理解がなく、同音異義語の誤変換が頻発する。
2. **フィラー（無意味なつなぎ言葉）の大量混入**:
   - 発話時の「えー」「あのー」「えっと」といった思考の隙間の言葉がそのまま文字として入力欄に吐き出され、手動でのテキスト修正コストが音声入力のタイピング削減メリットを上回ってしまう。
3. **OS・デスクトップ環境依存の入力制約と動作不安定性**:
   - X11 / Wayland のディスプレイサーバー制約により、グローバルホットキーの取得やアクティブウィンドウへの自動テキスト流し込み（ペースト）が環境によって動作しない。
   - Python の標準的なオーディオキャプチャ（PyAudio 等）ではバッファアンダーランやクラッシュが多発し、入力の信頼性が著しく損なわれていた。

### 1.3 本システムの提供価値（Core Value Proposition）
Voice In は、上記のペインを完全解消するために設計された**「エンジニアのための思考直結型・音声入力アシスタント」**である。

- **Hold-to-Talk（キー長押し即入力）**: 任意のキーを押している間だけバックグラウンド録音し、離した瞬間に超高速推論・自動貼り付け。UI操作を一切不要とする。
- **最新LLMによるフィラー完全除去 & 文脈補正**: Gemini 2.0 / Groq (Whisper + LLaMA 3.3) / Local Whisper を自在に選択可能。フィラーを痕跡なく削除し、カタカナ語を自然な英単語・IT用語へ自動変換。
- **コンテキスト認識プロンプト（Context-Awareness）**: 入力先アプリ（VSCode、Slack、Word、Terminal等）を瞬時に自動判別し、コードコメント・ビジネス敬語・ドキュメント調へプロンプトを動的最適化。
- **Rust (`cpal`) による低遅延・高堅牢オーディオコア**: ハードウェア直結の録音と VAD（無音検出）をネイティブコードで実行し、無駄なAPI課金と通信をゼロにする。

## 3. 業務フロー（As-Is vs To-Be）

### 従来の入力フロー (As-Is)
```
[思考] → [キーボード手入力] → [誤字修正] → [タイピング疲労]
または
[OS音声入力起動] → [発話] → [「えー」「あのー」混入] → [専門用語が誤変換] → [手動で消去・修正] (時間損失大)
```

### Voice In 導入後の業務フロー (To-Be)
```
[思考] → [キー長押ししながら発話] → [キーを離す]
   ↓ (自動バックグラウンド処理: 約0.8〜1.5秒)
[Rust録音完了] → [VAD無音判定] → [アクティブウィンドウ自動判定] 
   ↓
[AI推論（フィラー除去・専門用語英単語化・文体適正化）]
   ↓
[アクティブウィンドウへ自動 Ctrl+V 流し込み]
   ↓
[即座に作業完了！]
```

| :--- | :--- | :--- | :--- | :---: |
| **FR-001** | 入力制御 | グローバルホットキー | `pynput` を使用し、指定キー（`Left Alt`, `Right Alt`, `Left Ctrl`, `Right Ctrl`）の押下検知で録音開始、離脱で停止。 | P0 |
| **FR-002** | 音声処理 | Rust ネイティブ録音 | `cpal` によるハードウェア直結 44.1kHz 16bit PCM 録音。バッファリングと WAV 書き出しを Rust ネイティブスレッドで安全に実行。 | P0 |

| **FR-007** | 文脈最適化 | コンテキスト認識プロンプト | アクティブウィンドウ情報からカテゴリ（`DEV`, `BIZ`, `DOC`, `STD`）を自動検出し、単語境界マッチングで最適プロンプトを注入。 | P0 |

## 6. 前提条件・制約事項

1. **ディスプレイサーバー制約**:
   - Linux Wayland 環境では、セキュリティ仕様上 `xdotool` によるアクティブウィンドウ取得およびキー送信が制限される場合があるため、X11 環境を第一推奨とする。Wayland 環境ではクリップボード格納を主軸とし、キー送信はフォールバック機構（`pynput`）を用いる。
2. **マイク権限**:
   - OS ごとにマイクデバイスへのアクセス権限（Windows のプライバシー設定、macOS のマイク許可）が付与されている必要がある。
